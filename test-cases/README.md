# test-cases/

This is the **output of Stage 0** (Test Designer agent) and the **input to
Stage 1** (Explorer agent / script generation). Every test case here has a
stable ID, so it can be traced end-to-end: requirement → test case → spec
file → CI result.

## Structure

- One markdown file per feature, matching the requirements file it came
  from: `test-cases/checkout.md` ← `requirements/checkout.md`.
- Each test case gets an ID in the form `<FEATURE>-<NUMBER>`, e.g.
  `CHK-001`. IDs are never reused or renumbered once assigned — if a case is
  retired, mark it `[DEPRECATED]` rather than deleting the ID, so history
  and CI logs referencing it still make sense.
- `_traceability-matrix.md` is a single running table mapping every test
  case ID to its requirement source and its generated spec file. The Test
  Designer agent appends new rows here; the Explorer agent fills in the
  "Spec file" column once a case is automated.

## Test case fields

| Field | Meaning |
|---|---|
| ID | Stable identifier, e.g. `CHK-001` |
| Title | One-line description |
| Priority | P0 (blocker/smoke) / P1 (high) / P2 (medium) / P3 (low) |
| Type | Functional / Negative / Edge Case / Regression / API / Security / Accessibility |
| Preconditions | State the system must be in before the test starts |
| Steps | Numbered, concrete actions |
| Expected Result | What "pass" looks like, precisely |
| Automation Status | `Not automated` / `Automated` / `Flaky` / `Skipped (reason)` |
| Linked Spec | Path to the `.spec.ts` file once automated |

See `sample-checkout-test-cases.md` for a worked example generated from
`requirements/sample-checkout-requirements.md`.

## Review gate

Test cases generated by AI are a **draft**, not an approval. A QA lead (or
whoever owns quality on the team) should skim new/changed test cases before
they're handed to the Explorer agent for scripting — this is the one
manual checkpoint in an otherwise highly automated pipeline. See
`docs/07-TEST-CASE-GENERATION.md` and the `QA-BIBLE.md` review-gate section.
